# Steward · 个人生活管家 — 第一阶段产品需求

> 一句话定位：**我的个人生活管家**。
> 与 Deputy（事业助手：工作、项目、副业、学习、职业发展）相对应，
> Steward 负责我的**个人生活**。

---

## 1. 核心产品理念

Steward 不是记账工具，不是运动 App，不是"待维护的系统"。

它应该像一个真正了解我的生活管家：

- **输入足够轻**：我只需要自然地说"今天跑了 8 公里"、"晚上吃饭花了 368"，
  不需要想分类、选页面、填字段。
- **不只是记录，而是理解**：普通 App 告诉我数据，Steward 告诉我这些数据
  **意味着什么**。
- **越来越懂我**：使用三个月后，它应该比第一周时更懂我的正常消费水平、
  运动习惯和生活节奏，从而区分"正常波动"和"真正值得提醒的变化"。
- **改变行为**：最终目标是让我少花没必要的钱、更稳定地运动、
  更早发现生活状态的变化。

### 对比示例

| 普通 App | Steward |
|---|---|
| 本月跑步 31km | 本月跑步已比过去三个月均值高，但最近一周明显减少 |
| 本月餐饮消费 4200 元 | 本月餐饮比过去三个月均值高 22%，主要增长来自周末外出就餐 |

---

## 2. 第一阶段范围：只做 Finance + Fitness

**只做这两个方向，不要扩展。**

### 2.1 Finance（财务）

数据基础：复用已有的 **credi-insights** 项目（招行账单解析 + AI 分类 + MySQL 交易数据），
**不从零开始**。

Steward 要能回答：

- 这个月一共花了多少钱？钱主要花在哪里？
- 和上个月相比有什么变化？最近三个月消费趋势怎么样？
- 哪些消费增长比较明显？
- 有哪些固定支出 / 订阅 / 长期扣费？
- 最近有没有异常的大额消费？
- 哪些消费可以优化？
- 这个月的消费状态正常吗？
- 帮我复盘一下最近一个月的财务情况。

Steward 要能**主动发现**：

- 连续几个月餐饮支出上涨。
- 某类消费明显高于过去平均水平。
- 出现新的固定支出。
- 某些订阅长期存在但价值可能较低。
- 本月总支出增加但主要来自一次性大额（旅行/大件），并非日常消费失控。

核心理解目标：

> 我的钱平时是怎么花的，以及我的消费习惯正在发生什么变化。

### 2.2 Fitness（运动）

第一阶段只关注**运动本身**。不做医疗、疾病、健康诊断。

覆盖运动类型：跑步、健身、骑行、游泳、徒步、球类、其他体育活动。

**录入方式（最重要）**：不填表格。直接自然语言：

- "今天跑了 8 公里。"
- "今天健身一个小时，主要练胸和肩。"

Steward 要能回答：

- 这个月跑了多少公里？这个星期运动了几次？
- 最近一个月一共运动了多久？最近三个月运动频率怎么样？
- 我最近是不是运动少了？
- 这个月跑步目标完成得怎么样？
- 最近跑步和健身的比例有什么变化？

**目标管理**：支持简单目标（如每月跑 50km、每周至少运动 3 次、每月运动 12 次），
并持续知道：当前完成多少、还差多少、最近进度是否正常、是否需要调整安排。

Steward 要能发现趋势：

- 连续几周运动越来越少。
- 跑步明显增加但力量训练减少。
- 连续很多天没运动。
- 本月运动状态明显好于过去几个月。
- 某个目标即将完成或明显落后。

---

## 3. Review 是核心场景

第一阶段重点做 **Weekly Review** 和 **Monthly Review**。

月底我可以直接问："帮我复盘一下这个月。"

输出结构（Finance + Fitness 两个维度）：

**Finance**
- 这个月花了多少钱、主要花在哪里。
- 和过去相比有什么变化。
- 值得注意的消费、可以优化的地方。

**Fitness**
- 运动次数、总时长、跑量。
- 和过去相比的变化。
- 目标完成情况、状态在变好还是变差。

最后给出**少量真正值得行动的建议**（例如："下个月优先控制餐饮和订阅支出"、
"运动频率下降，先把每周三次恢复起来"）。

> 要求：不输出很多正确但没有价值的废话。有判断，有取舍。

## 4. 第一阶段跑通的真实场景（验收标准）

| # | 场景 | 验收 |
|---|---|---|
| 1 | 运动记录 | 说"今天跑了 8km"→ 问"这个月我跑多少了？"能正确回答 |
| 2 | 运动目标 | 说"这个月目标跑 50km"→ 之后能持续汇报完成情况 |
| 3 | 运动趋势 | 问"最近运动状态怎么样？"→ 结合最近几周/几个月，不是只答今天 |
| 4 | 消费分析 | 问"这个月钱主要花哪里去了？"→ 基于 credi-insights 数据回答 |
| 5 | 财务变化 | 问"最近消费是不是越来越高？"→ 结合历史数据给出判断 |
| 6 | 月度复盘 | 问"帮我复盘一下这个月"→ Finance + Fitness 综合，简洁、有判断、有行动建议 |

---

## 5. 成功标准（产品判断）

不看做了多少功能，看三件事：

1. **我愿不愿意持续告诉它我的事情** —— 输入必须自然、轻。
2. **它是不是真的越来越了解我** —— 三个月后比第一周更懂我的基线与节奏。
3. **它有没有真正改变我的行为** —— 少花冤枉钱、更稳定运动、更早发现变化、更容易坚持目标。

期望：一个可以**长期使用很多年**的个人生活管家。

---

## 6. 第一阶段明确不做

- Travel / Family / 情感
- 医疗健康（诊断、疾病等）
- 复杂资产管理、投资分析
- 大量生活分类

> 这些未来都可以加入，但现在不做。第一阶段把 Finance + Fitness 做好。

## 7. 已定架构（2026-10-16 确认）

```
你（微信）
   │
龙虾（OpenClaw）—— 脑子在这里，大模型与 token 都在龙虾侧
   │
   ├── MCP stdio → deputy        事业助手（工作/项目/学习）
   └── MCP stdio → steward       生活管家（Finance + Fitness）
                       │
                       └── MCP → credi-insights   财务数据源（背后的上游）
```

- **与 OpenClaw 联动**：Steward 是龙虾背后的纯逻辑后端（同 Deputy 模式），
  本身不配 AI、不烧 token。微信自然语言输入，龙虾经 MCP 调 Steward 记录/查询/复盘。
- **技术栈**：Python 3.12 + FastMCP(stdio) + SQLite + uv + pytest + ruff，完全对齐 Deputy。
- **Finance 数据**：Steward 作为 MCP client 挂载 credi-insights 的 `mcp-server.ts`，
  Finance 分析工具在其数据之上封装。**不直连其 MySQL，不复制数据**（同 Deputy↔feed-curator 关系）。
- **Fitness 数据**：Steward 自有 SQLite 库（`data/steward.db`，数据不出墙）。
- **开发流程**：OpenSpec + TDD + PR 门禁（对齐 Deputy / credi-insights 惯例）。
